Administration et récupération MFA : réserves techniques levées

407 contrôles exécutés : tous passent. S01 n’est pas encore déclaré clos.

Le MFA sur les anciennes commandes d’administration est actif dans Supabase local. La récupération complète d’un appareil perdu est implémentée et testée sur une restauration isolée. L’activation de son worker sur la pile source reste conditionnée à une configuration serveur dédiée.

Administration protégée

Les sept commandes exposées rights_change, rights_batch, share_create, share_accept, share_revoke, directory_authorize et admin_context exigent désormais une session AAL2 avec facteur approuvé, en plus des droits métier existants.

Les fonctions internes historiques ne sont pas exécutables directement par un utilisateur Auth (preuve). Un lecteur ordinaire sans MFA conserve la lecture d’un partage explicitement accepté pour lui, et perd cet accès après révocation. Aucun accès transversal implicite n’a été ajouté.

Effet sur la copie : ses appels d’administration en session mot de passe seul sont maintenant refusés. Les fichiers et le design du prototype sont intacts ; le frontal doit encore être raccordé au défi MFA dans S02.

Récupération après perte de l’appareil

  1. L’utilisateur demande la récupération des facteurs vérifiés encore enregistrés. La liste exacte est figée dans la demande.
  2. Un super administrateur distinct, explicitement habilité et connecté avec MFA, approuve après vérification humaine d’identité. La référence de cette vérification est conservée ; elle ne remplace pas la vérification humaine.
  3. Un worker séparé utilise l’API Auth officielle pour retirer uniquement les facteurs approuvés. Il vérifie l’autorisation avant chaque appel ; les demandes annulées, expirées ou déjà terminées sont refusées.
  4. Les anciennes sessions sont fermées. L’utilisateur se reconnecte et dispose d’une permission temporaire pour enrôler le remplacement. Le MFA reste obligatoire ; le nouvel accès métier attend la vérification du nouveau facteur.

Le test utilise une clé de service créée exclusivement pour une cible de restauration sans interface réseau ni port hôte. Aucun secret admin de la source n’est extrait et aucun facteur source n’est supprimé par ce worker. Les identités d’autres applications partageant Auth ne peuvent pas s’inscrire elles-mêmes à ce circuit UNIION.

La suppression d’un facteur utilise le mécanisme administratif officiel Supabase. Aucun utilisateur ni contenu métier n’est supprimé.

Une annulation peut empêcher les appels suivants ; elle ne peut pas annuler rétroactivement un appel Auth déjà en cours. Une reprise après erreur reste conditionnée à l’approbation, à la durée de validité et au bail du job.

Reste à faire

  1. Activation locale S01 : Fournir au worker Auth une configuration serveur dédiée et privée, puis qualifier son exécution supervisée sur la pile source et désigner les super administrateurs habilités. Le code et le parcours complet ont été testés sur une restauration isolée ; aucune configuration admin source n’a été fournie, donc le worker source reste désactivé.
  2. Qualification S01 : Finaliser la supervision de la file de révocation, le crash pendant une rotation du refresh token et le choix d’architecture de déploiement. Activation du worker : prérequis concret

Exemple sans secret. La vraie configuration doit rester dans un fichier privé hors publication, par exemple application/.local-auth/auth-admin.json, avec permissions 0600. Renseigner la clé serveur directement dans ce fichier, jamais dans le chat ou le navigateur. Le worker n’est pas chargé par l’application HTTP et ne suit pas les redirections réseau.

Exécution explicite après approbation : python -B operations/auth_recovery_worker.py ID_DE_DEMANDE --config CHEMIN_PRIVE. Sans configuration, l’exécution est refusée (preuve). Le rôle de service Supabase est puissant : son secret doit être réservé à ce processus d’exploitation.

Le serveur S01 conserve ses sessions durables sur 127.0.0.1:5060. Les conteneurs de recette sont arrêtés après les tests, leurs volumes et archives conservés. Aucun déploiement de production ni souscription effectué.
