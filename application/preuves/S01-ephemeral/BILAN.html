S01 · Pile neuve et transport réel du worker

26 octobre 2026. Prototype et S00 intacts : 834 empreintes vérifiées.

Réserves de qualification levées

  • Provisionnement automatique d’une base Supabase locale vide, sans lecture de la pile source, sans ports exposés et avec des identités fictives générées pour le test.
  • Rejeu des 24 migrations applicatives après les migrations Auth/Storage. Le gel des migrations Storage propre aux restaurations est désactivé pour cette cible neuve uniquement.
  • 13 contrôles : création/connexion, lecture propre, refus de lecture et d’écriture entre organisations, révocation d’appartenance.
  • 44 contrôles de récupération MFA sur restauration isolée, dont l’exécution du véritable ServerTransport HTTP et l’appel à l’API officielle Auth pour le facteur approuvé. Clé temporaire confinée à la cible, configuration privée en mémoire temporaire du conteneur, aucun secret source lu.
  • 102 tests unitaires Linux et contrôle des frontières réussis.

Total : 159 contrôles distincts. La commande combinée est également rejouée pour vérifier le provisionnement sur une seconde base neuve, sans additionner les mêmes tests au total.

Commande locale reproductible

Depuis application, construire une fois l’image : docker build -t uniion-quality:local -f ci/Dockerfile ci, puis lancer avec le runtime Python qualifié et Docker dans PATH : python3 -B scripts/local_integration_gate.py.

Cette commande exécute le contrôle Linux puis la pile neuve. Les images PostgreSQL, Auth, REST et Storage sont celles fixées dans les outils. Les conteneurs sont arrêtés après chaque essai ; les volumes sont conservés. Aucune purge automatique. Leur suppression ultérieure nécessite une validation super admin.

Le test de récupération complet reste une commande distincte : python3 -B operations/lost_factor_drill.py. Il sauvegarde la pile locale puis restaure une cible isolée ; il ne fait donc pas partie du contrôle CI sans source.

Ce qui reste réellement

  1. Activation du worker sur la pile source : le code et son transport réel sont qualifiés ; aucune clé dédiée n’est configurée pour cette pile. L’activation et un essai sur ses comptes fictifs restent à effectuer lorsque cette configuration sera disponible. Aucune clé n’a été extraite automatiquement.
  2. Compléter la couverture CI : la pile neuve valide les migrations et les droits de base. Les parcours avancés de partage, pièces jointes, antivirus et récupération MFA doivent encore être portés sur ses fixtures autonomes. Leurs preuves antérieures sur la pile locale ne constituent pas des tests CI neufs.
  3. Développement suivant : portage des écrans/modules, écritures métier, stockage hors ligne sécurisé et synchronisation, comparaisons visuelles sur les trois formats.
  4. Production différée : CI distante, OVH/Supabase managé, HTTPS, secrets, sauvegardes hors site et recette de la topologie cible restent documentés, non déployés.

S01 conserve ces réserves explicites. Ce bilan ne prétend ni livrer toute l’application ni valider tous les parcours métier de production.
